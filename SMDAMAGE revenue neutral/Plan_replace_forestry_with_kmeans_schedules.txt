Plan: replace the 9 forestry bidders in Forestry_bid_steps.csv with the 71 k-means forestry schedules

Reviewed files
- Data/Forestry_bid_steps.csv currently stores one shared quantity column plus 9 forestry price columns.
- SMDAMAGE revenue neutral.py lines 128-132 currently impose one aggregate land constraint across all forestry bidders with units == mhectares.
- create_database.py currently hardcodes the 9 forestry bidders as a multi-column CSV layout with fixed column indices and a shared quantity column.
- The live Busch SQLite stores selected_rotation_year, cluster_index, area_ha, crop_va_USD_per_ha_per_year, selected_establishment_cost_USD_per_ha, and p_USD_per_tC_harvested in Undiscounted_dta_output. The older Busch lineage shows the upstream cost inputs nr_cost, ep_cost, np_cost, crop_va, and p, but the live SMDAMAGE-ready SQLite has already collapsed establishment cost to selected_establishment_cost_USD_per_ha.

Main conclusion
The Forestry_bid_steps.csv structure should be changed. The current wide format was barely tolerable for 9 forestry types, but it is a poor fit for 71 schedules because:
- it hardcodes bidder identities into create_database.py column indices
- it assumes one shared quantity column for all forestry bidders
- it does not naturally carry bidder-specific metadata like rotation year, cluster index, or available area
- it will become fragile and hard to audit with 71 price columns

Recommended data structure
Do not keep one wide Forestry_bid_steps.csv with 71 price columns.
Instead move forestry inputs to normalized long-format files, ideally three files:

1. forestry_bidder_metadata.csv
Columns:
- bidder_name
- rotation_year
- cluster_index
- contract_years
- available_area_mhectares
- hector_name
- description
- source_run or provenance tag if desired

2. forestry_bid_steps_long.csv
Columns:
- bidder_name
- bid_step
- price_per_hectare
- quantity_mhectares

3. forestry_sequestration_long.csv
Columns:
- bidder_name
- year
- tons_per_hectare_per_year

Notes:
- bidder_name can encode rotation year and cluster, for example Forestry_r10_c03.
- contract_years should usually equal rotation_year for these clustered schedules.
- available_area_mhectares should come from the k-means summary output for each schedule.
- If you want to keep a single CSV for convenience, it should still be long format, not wide.

Why this is better
- create_database.py can load 71 bidders without hardcoded price_col indexes
- each forestry schedule can carry its own available area and contract length
- the SMDAMAGE database tables bidders, bids, and forestry_removal are already closer to long format than the current source CSV
- the k-means outputs already naturally identify schedules by selected_rotation_year and cluster_index

Planned implementation steps

A. Create 71 forestry bidder identities from the k-means results
- Source from Busch2024_to_SMDAMAGE.sqlite tables carbon_removal_schedules and Undiscounted_dta_output.
- One bidder per combination of selected_rotation_year and cluster_index.
- Expected counts from current k-means work: 12 schedules for rotation year 6, 32 for 10, 20 for 17, and 7 for 35, totaling 71.
- Create bidder_name values that are stable and sortable, such as Forestry_r06_c00, Forestry_r10_c31, and so on.

B. Build the sequestration schedule file
- For each bidder, read carbon_removal_schedules rows by selected_rotation_year and cluster_index.
- Map selected_rotation_year to contract_years.
- Write year and tC_per_ha_per_year for each bidder.
- Convert units only if SMDAMAGE needs a different naming convention; conceptually this is still tons per hectare per year.

C. Build the available-area metadata
- For each bidder, take total_area_ha from carbon_removal_schedules or the k-means summary CSV and convert to million hectares.
- available_area_mhectares = total_area_ha / 1_000_000.
- This area should be bidder-specific, not shared across all forestry schedules.

D. Build the forestry bid-step cost curves
Goal:
- replace the old 9 forestry price columns with 71 bidder-specific price schedules in dollars per hectare

Recommended source logic
- Start from per-pixel rows in Busch2024_to_SMDAMAGE.sqlite joined to their selected_rotation_year and cluster_index.
- Use the live SMDAMAGE-ready fields where possible:
  - crop_va_USD_per_ha_per_year
  - selected_establishment_cost_USD_per_ha
  - p_USD_per_tC_harvested
  - area_ha
- If exact decomposition into nr_cost + ep_cost + np_cost is still required, pull those fields from the upstream Busch inputs or recreate them from the legacy Busch pipeline rather than guessing from the collapsed output table.

Cost formula recommendation
- Use bidder price per hectare = NPV_Y(crop_va_USD_per_ha_per_year, discount_rate) + selected_establishment_cost_USD_per_ha - harvest_revenue_per_ha
- If you insist on the original decomposition, use:
  Bid cost per hectare = NPV(contract length Y, crop_va) + establishment cost component - harvest revenue component
  where establishment cost component is nr_cost or the relevant plantation cost logic, and harvest revenue component is p times harvested tC per hectare if harvest revenue is represented explicitly.

Important caution
- The live SMDAMAGE-ready SQLite does not visibly store raw nr_cost, ep_cost, and np_cost columns. It stores selected_establishment_cost_USD_per_ha instead.
- Therefore, for this workflow, the practical first pass is to use selected_establishment_cost_USD_per_ha unless you deliberately rejoin to the upstream Busch inputs.

E. Convert per-pixel costs into bid steps
- Within each bidder schedule, sort pixels by cost per hectare ascending if lower cost means more attractive removal.
- Accumulate area_ha to form bid steps.
- Decide on a bid-step granularity. Two reasonable options:
  - keep the old constant step size approach, for example fixed increments of area
  - use one row per distinct pixel group and let steps vary by available area
- Write price_per_hectare and quantity_mhectares for each bid_step and bidder_name.

Recommendation on step granularity
- Prefer long-format variable bid steps rather than forcing every bidder to share the old fixed quantity increments.
- With 71 schedules and very different available areas, forcing the same step grid on all bidders is not very natural.

F. Change create_database.py
Current problem:
- forestry is loaded from a hardcoded wide CSV with 9 configured bidders and one shared quantity column.

Recommended change:
- stop treating forestry as a special multi-column bidder file
- add a new loader for long-format forestry bidder metadata, long-format forestry bid steps, and long-format forestry sequestration
- insert bidder rows directly into bidders
- insert bid rows directly into bids
- insert sequestration rows directly into forestry_removal

G. Add SMDAMAGE land constraints for each contract type
Current logic in lines 128-132:
- imposes one aggregate land constraint across all forestry bidders combined

Needed logic:
- impose one land-availability constraint per forestry bidder, using that bidder's available area
- conceptual form for each forestry bidder f and model period t:
  sum of vpt[f, u] over all bid years u that are active in period t <= available_area_mhectares[f]
- active means u <= t and t < u + contract_years[f]

Why this matters
- once the 71 schedules are disjoint schedule-specific land pools, each contract type needs its own land cap
- otherwise the model can overuse a bidder-specific schedule beyond its available area as long as the total across all forestry bidders stays within the aggregate cap

H. Optional aggregate check
- You may keep an additional aggregate forestry land constraint as a diagnostic, but the bidder-specific constraints are the important ones.
- If the 71 schedules partition the available pixels cleanly, the aggregate constraint is redundant once bidder-specific caps exist.

Suggested coding sequence
1. Export a normalized 71-bidder forestry metadata file from the Busch k-means outputs.
2. Export a normalized 71-bidder sequestration file from carbon_removal_schedules.
3. Export a normalized 71-bidder bid-step file from per-pixel costs and areas.
4. Refactor create_database.py to load the new long-format forestry files.
5. Add bidder-specific land constraints in SMDAMAGE revenue neutral.py.
6. Rebuild the SMDAMAGE database.
7. Run a smoke test and verify:
   - 71 forestry bidders appear in bidders
   - bids exist for each forestry bidder
   - forestry_removal has rows for each bidder and year
   - no bidder exceeds its available_area_mhectares in the optimized solution

Structure recommendation in one sentence
Yes, change Forestry_bid_steps.csv from the current wide shared-quantity format to a normalized long-format forestry input design, because the k-means replacement introduces bidder-specific contract lengths, areas, and schedules that the current 9-column layout does not represent cleanly.
